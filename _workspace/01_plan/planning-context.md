# Planning Context

## Current Planning Memo

**대상 화면/기능** — 미니4WD 트랙 공유 URL을 넣으면 그 트랙을 3D로 세워 보여주는 단일 화면.
360도 회전·확대축소, 슬로프/뱅크의 고저차 입체 표현, START부터 트랙을 따라가는 시점,
레인체인지 표현.

**주 사용자와 목적** — 코스 분석·연습 계획. 도면(2D)으로는 감이 오지 않는 **구간별 고저차와
연속 코너**를 눈으로 확인해 세팅·주행 전략을 세운다. 관람용 3D가 아니라 **판단 근거**다.

**확인된 요구사항** (사용자 확정, 2026-08-28)
- 입력: 편집기 공유 URL → **서버가 가져와 파싱**
- MVP 4종 전부: ① 도면과 일치하는 트랙 형상 ② 슬로프·뱅크 높이가 입체로 ③ 트랙을 따라가는
  시점 ④ 레인체인지 표현
- 저장 없음 — 붙여넣고 보면 끝. 계정·목록·메모 없음
- 고저차 근거는 실물 피스 규격에서 가져온다(그럴듯한 값 가정 아님)

**빠진 상태·시나리오** (Phase 1에서 채운다)
- 잘못된 URL / 없는 트랙 코드 / 편집기 응답 실패 / 파싱 실패
- 폐곡선이 아닌 트랙(끝점이 안 맞는 배치) — 편집기는 미완성 트랙도 저장할 수 있다
- 아주 큰 트랙에서의 렌더 성능
- 데이터에 있으나 사용자가 언급하지 않은 피스 타입(wave, jump, digital curve, r2100 등)

**가정과 검증 방법** — `decision-log.md` 참조.

**상대 노력도** — `L`.
- driver: ① 진행 순서 복원 알고리즘(끝점 매칭 + 폐곡선 검증) ② 고저차 모델(피스 타입·색 →
  높이 프로파일) ③ 3D 렌더 + 카메라 2종(오빗 / 트랙 추종) ④ 레인 단위 모델(레인체인지)
  ⑤ 외부 편집기 fetch 경로(serverless)
- 권고: **`split`**. ①②③(오빗까지)이 독립적으로 쓸모 있는 최소 단위다. ④ 레인체인지는
  레인 단위 모델을 요구해 데이터 구조를 한 단계 복잡하게 만든다 — 2차로 미루면 1차가 빨리
  손에 들어온다. 사용자가 MVP 4종을 모두 필수로 지정했으므로 **이 권고는 제안이며
  결정은 Phase 1 체크포인트에서 받는다.**
- 최소 가시 검토 단위: 참조 트랙 WS67Y2 하나가 3D로 뜨고 회전·확대가 되는 것

## UX Check

- **첫눈에 알 수 있어야 하는 것**: 이 트랙이 도면의 그 트랙이라는 것(형상 일치),
  그리고 어디가 올라가고 어디가 내려가는지.
- **다음 행동이 보이는가**: 붙여넣기 → 3D. 그 다음 "따라가며 보기"로 넘어가는 길이 보여야 한다.
- **실수하거나 오해할 지점**: **고저차 값이 추정치인데 실측처럼 보이는 것.** 코스 분석이
  목적이라 이 오해는 실제 세팅 판단을 틀리게 만든다 — 근거 등급을 화면에 표기해야 한다.
  또 하나: 3D가 실제 주행감(속도·관성)을 보여준다는 오해. 이건 기하 표현이지 시뮬레이션이 아니다.
- **먼저 정할 방향**: 트랙 추종 시점의 형태(1인칭 주행 시점인가, 구간을 따라가는 카메라인가)와
  고저차를 읽는 보조 표현(측면 프로파일 그래프 등)이 필요한가.
- **prototype/Phase 2에서 확인할 것**: 회전·확대 조작감, 고저차가 실제로 "읽히는지"
  (색만으로 충분한지 아니면 높이 눈금이 필요한지), 추종 시점의 어지러움.
