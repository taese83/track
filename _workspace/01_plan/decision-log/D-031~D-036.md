## D-032 · 웨이브는 고도가 아니라 **평면상 옆으로 튀어나온 곡면** (2026-08-29, 사용자 지정)

> "웨이브는 1개의 직선 트랙에서 오른쪽이 튀어나온 형태로 그려야해,
>  양 끝은 직선이고 그 내부가 오른쪽으로 튀어나온 트랙"

### 종전이 틀린 이유

`Chi1`을 **세로 5cm 범프**(고도)로 그렸다. 오독이다.

**편집기는 위에서 내려다본 2D 도면이고 고도를 그릴 수단이 없다.** 슬로프(`Bri1`)조차
평평하게 그리고 **색으로만** 오르내림을 표시한다. 그렇다면 `Chi1` 이미지에서 띠가
눈에 보이게 휘어 있는 것은 **평면상 휘어진 것**일 수밖에 없다.

정황 셋이 같은 방향을 가리킨다:

| 근거 | 내용 |
|---|---|
| 이미지 높이 | `Chi1`만 42px (다른 3레인 피스는 36) — 옆으로 빠질 여유분 6px |
| 정점 좌표 | `Chi1: [[-27,3],[27,3]]` — 양 끝이 y로 +3 치우침 |
| 색 | WS67Y2의 `Chi1`은 c=0 (고도 변화를 뜻하는 c=2/c=3이 아님) |

### 모양은 사인이 아니라 **삼각형**

픽셀 측정이 **일정한 기울기**로 들어갔다 나온다:
`top` = 6→5→4→3→2→**1**→2→3→4→5→6. 사인 곡선이면 양 끝이 완만해야 한다.
직선 두 개(들어가는 램프 · 나오는 램프)여야 "양 끝은 직선"과도 맞는다.

`bow(t) = (1 − |2t − 1|) × 5cm`, 진행 방향 기준 **오른쪽**.

### 실측

| 항목 | 값 |
|---|---|
| 옆으로 밀린 양 | `0,1,2,3,4,5,4,3,2,1,0` cm (측정 프로파일과 일치) |
| 방향 | **오른쪽** (진행 방향 기준, 두 피스 모두) |
| 고도 변화 | **0** (평평) |
| 레인 폭 | 24cm 보존 |
| 폐합 · 이음새 | finalZ 0 · 벌어진 이음새 7(꼬리, 불변) |

### 개정 (같은 날, 사용자 재지정)

> "지금 웨이브를 반대로 튀어나오게 하고 각진것이 아니라 곡면으로 그리고 좀더 튀어나오게"

| 항목 | 1차 | **확정** |
|---|---|---|
| 방향 | 오른쪽 | **왼쪽** |
| 모양 | 삼각형 `1 − |2t − 1|` | **곡면** `sin²(πt)` |
| 돌출량 | 5cm (픽셀 측정) | **5cm** (픽셀 측정값과 일치) |

`sin²`는 양 끝 기울기가 0이라 앞뒤 직선과 매끄럽게 잇고 마루도 각지지 않는다 —
"양 끝은 직선"과 "각진 것이 아니라 곡면"을 동시에 만족한다.

돌출량은 10 → 8 → 6.5을 거쳐 **5cm로 되돌아왔고, 픽셀 측정값과 정확히 일치한다.** 크기 등급은
`measured`이고, 방향(왼쪽)과 모양(곡면)은 사용자 지정 `confirmed`다. 구현은 `geom3d.js`의
`waveAmp`(크기)와 `waveSide`(방향) 두 상수이며 각각 한 줄이다.

## D-033 · 레인체인지는 레인이 **한 칸씩 순환**하는 교차 형상 (2026-08-29, 사용자 지정)

> "레인이 실제로 자리를 맞바꾸는 형상으로 그려줘"

### 모델

`Lan1`(162cm) 구간에서 세 레인이 한 칸씩 순환한다 — 레인0→1, 레인1→2, 레인2→0.
바깥으로 밀려난 레인2가 나머지 둘을 **가로지르며** 반대편으로 넘어가는 것이 교차 형상이다.

자리바꿈 곡선은 양 끝 기울기 0의 S곡선 `(1−cos πt)/2` — 앞뒤 직선 구간과 매끄럽게 잇는다.
고도 변화는 없다.

### 왜 "한 칸 순환"인가

공식 API가 근거다(`00_source/piece-shapes.md` 추가 실측):

```
"changers": 1,  "order": [1,2,3]
```

문서는 `order`를 "차가 지나가는 레인 순서"로 정의한다. changer 하나로 `[1,2,3]`이
나오려면 changer가 레인을 **한 칸씩 밀어야** 한다. 좌우 대칭 교환(0↔2, 1 고정)이면
두 바퀴 만에 원위치라 세 레인을 다 돌 수 없다.

픽셀 측정과도 맞는다 — `Lan1` 이미지 중앙부에서 띠 높이가 36→30px로 좁아진다.
레인들이 겹쳐 보이는 구간이며, 길이가 다른 피스의 3배(162cm)인 것도 교차에 그만큼
거리가 필요하기 때문이다.

### 실측 (WS67Y2)

| 항목 | 값 |
|---|---|
| 레인 가로 위치 | `[−12, 0, +12]` → **`[0, +12, −12]`** cm |
| 위치 집합 보존 | ✓ 세 자리가 그대로 채워진다 |
| 교차 횟수 | lane1×lane2 **1회**, lane0×lane2 **1회**, lane0×lane1 0회 |
| 길이 | 162.0 cm |
| 고도 변화 | 없음 |

### 측정 실수 기록

처음 검증에서 끝 위치가 `[−12, 0, −24]`로 나와 구현이 틀린 줄 알았다. **측정이 틀렸다** —
가로 위치의 기준선을 레인1의 현으로 잡았는데, 레인1 자신이 옆으로 움직이므로 그 기준에서는
레인1의 이동량이 항상 0으로 나온다. 피스의 원래 진행축(`p1`→`p2`)으로 바꾸니 맞았다.

**움직이는 것을 기준으로 삼으면 그 움직임이 측정에서 사라진다.** PC-011에 적은
"측정 범위를 결과와 같은 기준으로 잡아라"와 같은 계열의 실수다.

## D-034 · 트랙 폭 결함 — 그려진 폭이 36cm가 아니라 24cm였다 (2026-08-29, 사용자 지시로 확인)

> "트랙의 폭을 확인하고 레인을 선이 아닌 공간으로 그려줘"

### 결함

`TRACK_WIDTH` 상수는 36cm(3레인 × 12cm)인데 **실제로 그려진 면은 24cm**였다.

원인: 트랙 면 폴리곤을 **바깥 레인 두 개의 중심선**(레인0 중심 ↔ 레인2 중심)으로 만들었다.
중심선 사이 거리는 2 × 12 = 24cm다. **양쪽 바깥 반 레인(6cm씩)이 통째로 빠졌다.**

상수와 렌더가 12cm 어긋난 채로 계속 "3레인 폭 36cm"라고 화면에 표기하고 있었다 —
고지 문구가 실제와 달랐다.

### 수정 — 레인은 선이 아니라 면이다

`buildLanes`가 레인마다 좌·우 가장자리(`bands[L] = [lo, hi]`)를 함께 만든다.
가장자리는 중심선과 **같은 규칙**(웨이브 활 · 레인체인지 자리바꿈 · 평면 고도)으로
생성되므로, 레인체인지 구간에서는 레인 면 전체가 자리를 옮긴다.

렌더는 면 1개 + 중심선 3줄 → **레인 면 3개 + 경계선 4줄**로 바뀌었다.

### 실측 (수정 후)

| 항목 | 값 |
|---|---|
| 전체 폭 | **36.0 cm** = `TRACK_WIDTH` 상수와 일치 |
| 레인별 폭 | **12 / 12 / 12 cm** |
| 인접 레인 사이 틈 | **0.000 cm** (빈틈 없음) |
| 레인 면 개수 | 396 = 132 피스 × 3 레인 |
| 경계선 개수 | 528 = 132 × 4 |
| 콘솔 에러 | 0 |

### 관찰

이 결함은 **숫자로만 드러났다.** 화면에서는 24cm도 36cm도 그럴듯한 트랙으로 보인다.
`TRACK_WIDTH` 상수와 실제 렌더 폭을 대조하는 한 줄이 없었다면 계속 지나쳤을 것이다.
**상수와 렌더 결과를 대조하는 단언**이 필요한 자리다.

## D-035 · 레인체인지의 3→1 레인은 **육교**다 (2026-08-29, 사용자 지정)

> "3→1로 가는 구간을 위로 올라가는 언덕으로"

### 모델

레인체인지에서 트랙 폭을 **두 칸 건너뛰는** 레인(현재 순환 1→2, 2→3, 3→1에서 **3→1**)은
나머지 둘 **위로** 넘어간다. 같은 높이로 지나가면 서로 통과해 버리므로 실제로는 육교다.

높이 `+8cm`, 모양 `sin²(πt)` — 양 끝 기울기 0이라 앞뒤와 매끄럽게 잇고 끝에서 0으로
돌아온다. 나머지 두 레인(1→2, 2→3)은 고도 변화가 없다.

`geom3d.js`의 `changerHill` 상수 한 줄이다. 0을 주면 평면 교차로 돌아간다.

### 실측 (WS67Y2)

| 레인 | 경로 | 최대 높이 |
|---|---|---|
| | 1 → 2 | 0 |
| | 2 → 3 | 0 |
| **육교** | **3 → 1** | **+8 cm** |

교차 지점에서 다른 레인보다 최소 **6 cm** 위. 고도 불연속 0, 최종 누적 z 0(폐합).

### 부호를 세 번 왕복한 기록 — 진단 그림이 오히려 방해가 됐다

| 시도 | 조치 | 결과 |
|---|---|---|
| 1 | 육교 `+8` | **실제로는 맞았다** |
| 2 | 사용자 "1→3" 지적 → 순환 방향 반전 | **엉뚱한 레인**을 올림 |
| 3 | 사용자 "축이 반대" 지적 → 전역 z 반전 | 전부 뒤집혀 더 나빠짐 |
| 4 | 전역 반전 원복 + 육교만 `−8` | 여전히 반대 |
| 5 | **`+8` 복귀** | 확정 |

**축은 처음부터 정상이었다.** `+z`는 화면 위가 맞다(투영 검사·축 화살표 모두 확인).

교훈 두 가지:

1. **첫 지적 때 곧바로 코드를 고친 것이 잘못이었다.** "1→3"이라는 말이 내 순환(3→1)과
   어긋난다는 것을 먼저 확인했어야 했다. 용어가 어긋난 채로 세 번을 고쳤다.
2. **진단 그림이 오해를 키웠다.** 깊이 정렬과 4배 과장을 넣은 옆면 그림은 언덕 방향을
   실제와 반대로 읽히게 만들었다 — 사용자가 "네가 그린 것은 언덕이 반대"라고 지적했다.
   **판정 근거로 쓸 그림은 앱과 같은 조건으로 그려야 한다.** 과장·정렬·시점을 바꾼 그림은
   설명용이지 판정용이 아니다.

앞서 PC-011에 "형상은 형상으로 물어라"라고 적었는데, 이번엔 **잘못 그린 형상이 오히려
판정을 흐렸다.** 그 규칙에 "앱과 동일 조건"이라는 단서를 붙여야 한다.

## D-039 · 입체교차 판별 — **좌표 정확 일치가 1순위** (2026-08-29, 사용자 지적으로 발견)

### 문제

네 개의 트랙 끝이 한 점에 모이는 입체교차에서 어느 둘이 실제로 물린 이음새인지 판별하지
못했다. 사용자가 "108번은 124번 코너로 이어져야 한다"고 지적했으나, 우리 알고리즘은
계속 `Str1(658,600)`을 골랐다.

시도한 근거가 전부 실패했다:

| 근거 | 결과 |
|---|---|
| 진행 방향 연속성(현) | 구분 못 함 |
| 실제 접선으로 교체 | 구분 못 함 — **틀린 쪽이 더 직진**(2.8° vs 5.6°) |
| 폐곡선 완주(132개) | 두 답 모두 통과 |
| 총 회전량(1080°=3바퀴) | 두 답 모두 통과 |
| 겹침 구간 수직 이격 | 두 답 모두 19.5cm |
| 편집기 도면 4.6배 확대 | 해상도로 판별 불가 |

### 원인 — 우리가 신호를 지웠다

원자료를 소수점까지 보니 네 끝점이 **두 무리로 정확히 갈려** 있었다:

| 무리 | 좌표 |
|---|---|
| 108번 진출 · **124번 `Cor1(666,601)`** | **(658.00, 627.00)** |
| `Str1(658,600)` · `Cor1(650,653)` | **(658.02, 626.95)** |

차이 **0.06cm**. 편집기는 실제로 물린 이음새의 좌표를 **소수점까지 똑같이** 저장한다.
즉 답은 처음부터 데이터에 있었다.

우리 `TOL = 3cm` 양자화가 이 구분을 지웠다. **실제 오차의 50배**로 잡은 값이다.
지운 뒤에는 각도로 고를 수밖에 없었고, 하필 각도로는 틀린 쪽이 더 직진이라 복구가
불가능했다.

### 수정

분기 후보를 **두 단계로** 고른다:

1. **좌표가 가장 가까운 무리**(정확 일치)를 먼저 고른다.
2. 같은 무리(0.02cm 이내) 안에서만 접선 연속성으로 가른다.

특정 트랙에 맞춘 보정이 아니라 편집기 데이터의 성질을 쓰는 일반 규칙이다.

### 실측 (수정 후)

| 항목 | 값 |
|---|---|
| 108번 다음 | **`Cor1(666,601)`** — 사용자 지정과 일치 |
| 복원 피스 | 132 / 132 |
| 폐합 | 닫힘 |
| 출발 방향 | 화살표 방향 |
| 최대 이음새 거리 | 22.33cm (D-038에서 이어붙인 대각 직선 한 곳뿐) |

### 교훈

**허용오차는 "넉넉히"가 아니라 정보를 버리는 결정이다.** 버린 정보가 유일한 판별 근거였다는
사실은 판별에 실패한 뒤에야 드러난다.

앞서 "끝점 264개 중 262개가 0.5cm 안에 짝이 있다"는 측정을 이미 해놓고도 그 함의를 읽지
못했다. **허용오차를 정하기 전에 실제 오차 분포를 먼저 찍어야 한다.**
