# Decision Log — PC-010~050

## PC-010 · 뷰어 조작 결함 3건 + 높이 정정 (2026-08-29, 사용자 지적 3건)

사용자 지적: ①"움직임이 너무 느린데 프리뷰라서 그런거지?" ②"x y z 축 360도로"
③"슬로프 높이가 조금 과해". ①은 **프리뷰 탓이 아니었다**.

### ① 드래그가 느린 게 아니라 아무것도 안 그리고 있었다 — 내가 만든 회귀

측정부터 했다. 재도색 1회 = **중앙값 3.2ms**(60fps 예산 16.7ms의 1/5). 성능 문제가 아니다.

원인은 `renderCanvasOnlyOrbit()`이 **빈 함수**였다는 것. 3D 재작업(PC-008) 때 종전
`g.setAttribute('transform', rotate(...))` 한 줄을 지우면서 주석만 남기고 대체 구현을
넣지 않았다. 패치 스크립트의 단계 이름이 문자 그대로 **"orbit-only 갱신 무력화"**였다 —
무력화해 놓고 복구를 잊었다.

증상이 "안 움직임"이 아니라 "느림"으로 보인 이유: 방향키는 `render()`(전체 재렌더)를
불러서 동작했고, 드래그만 죽어 있었다.

**수정** — SVG 요소는 유지하고 내용만 다시 그린다. 요소를 통째로 갈아끼우면
(`renderViewerBody()`) 드래그 중 pointer capture와 리스너가 끊긴다:
`paint()`를 `svgEl.__whRepaint`로 노출하고, `renderCanvasOnlyOrbit()`은 rAF로 프레임당
1회만 호출한다. 방향키·휠·`+`/`-`도 전체 재렌더에서 이 경량 경로로 옮겼다 —
회전·확대는 캔버스 밖 표면을 바꾸지 않는다.

**딸려 나온 결함**: 드래그 중 구간 집기가 `nearestIndexByXY(segs, rx, ry)`로
**편집기 원좌표**와 비교하고 있었다. 3D 재작업으로 `<g transform="rotate">`가 사라졌는데
역회전 보정 코드는 남아 있었다. 투영 좌표 기준(`__whCenters`)으로 교체했다.

### ② x축이 0~89도로 잠겨 있었다

`Math.max(0, Math.min(89, ...))`. 트랙을 **아래에서 올려다볼 수 없었다.**
세 축 모두 `wrap360`으로 바꿨다. 조작 안내 문구에 축을 명시했다(종전 "방향키: 회전"만
있어 어느 키가 어느 축인지 알 수 없었다).

검증(6도씩 60회 = 한 바퀴): x 58→118→178→238→298→358→58, 서로 다른 각도 60개,
**전 단계에서 132면 유지**. y는 0→90→180→270→0, z는 0→120→240→0으로 순환.

### ③ 높이 → D-023 (별도 엔트리)

`tan` → `sin` 정정. 슬로프 45.3 → **34.7cm**(−23%), 뱅크 10.2 → **9.6cm**.
근거와 파생 문서 갱신은 `D-023~D-030.md` 참조.

### 검증 (수정 후)

| 항목 | 값 |
|---|---|
| 재도색 1프레임 | 3.2ms (max 5.9) |
| 벌어진 이음새 | 7 / 131 (전부 순서 미확정 꼬리) |
| 고도 불연속 | 0건 |
| 최종 누적 z | 0.0 (폐합) |
| z 범위 | −34.7 ~ 0 |
| 3축 360도 | x·y·z 전부 순환 확인 |

### 하네스 관찰 (PC-009에 이어)

PC-009와 **같은 계열의 결함이 또 나왔다**: 재작업이 기존 동작을 조용히 죽였는데
게이트도 육안 검수도 잡지 못했다. 이번엔 내가 "무력화"라고 이름 붙인 패치 단계가
그대로 남았다는 점에서 더 나쁘다.

공통 성질: **없어진 동작은 화면에 아무 흔적을 남기지 않는다.** 잘못 그려진 것은 보이지만
안 그려진 것은 안 보인다. 프리뷰 검증이 스크린샷 중심인 한 이 계열은 계속 샌다.
필요한 것은 **동작 단언**(드래그 → 각도 변화, 이음새 연속성, 축별 360도 순환)이며,
이번에 쓴 측정들이 그대로 그 단언의 초안이다.

## PC-011 · 뱅크 모델을 세 번 고쳐 쓴 과정 (2026-08-29)

한 번에 맞히지 못했다. 기록해 둘 값어치가 있는 것은 **무엇이 판정을 갈랐는가**다.

| 회차 | 구현 | 사용자 반응 |
|---|---|---|
| 1 | 롤 0→20° 로그 전이 + 이후 유지 | "뱅크 구현이 잘못되었어… 트랙이 휘어지는 것은 아니야" |
| 2 | 롤 20° 균일(피스 안 일정) | (A/B 비교 제시) → **C 선택** |
| 3 | **경사(pitch) 인계** — 롤 폐기 | 확정 |

근본 원인은 **"기울어지게"를 롤로 읽은 것**이다(D-024 오독). 사용자가 말한 20°는
좌우 눕힘이 아니라 진행 방향 경사였다. 1·2회차는 같은 오독 위에서 형태만 바꾼 것이라
둘 다 틀릴 수밖에 없었다.

### 무엇이 판정을 갈랐나

**말이 아니라 그림과 숫자다.**

- 2회차에서 A/B를 **나란히 렌더해 보여준 뒤에야** 방향이 잡혔다. 그 전까지는
  텍스트로 두 번 주고받으며 서로 다른 것을 가리키고 있었다.
- 3회차에서 "경사를 트랙 끝까지 이어간다" 해석은 **폐곡선이 132.3cm 어긋난다**는
  수치가 즉시 기각했다. 이웃 한 피스로 한정하니 0.0으로 닫혔다.
  **닫힘 여부가 해석을 판별하는 무료 검증기였다.**

### 반성

사용자 지적("잘못되었어")을 받고 **곧바로 두 번째 구현으로 넘어간 것이 성급했다.**
첫 지적 시점에 A/B를 그려 보여줬다면 왕복 한 번을 줄였다. 텍스트로 형상을 합의하려는
시도 자체가 비용이었다 — 형상 문제는 형상으로 물어야 한다.

또 롤 부호를 "혼재(9/13)"라고 보고했다가 정정했다. 롤이 걸리지 않은 피스까지 범위에
넣고 센 **측정 자체의 결함**이었다. 실제로는 8/8 전부 정상이었다. 측정 범위를 결과와
같은 기준으로 잡지 않으면 없는 결함을 만들어낸다.

### 부수 확인

- 롤이 폐기되면서 `ASSUMPTION-008`(롤 부호)은 소멸했다.
- 슬로프 각도는 D-025로 25°(피스당 22.8cm). 트랙 z 범위 −23.7~0.

## PC-012 · 구간 목록이 뷰어 높이를 넘긴 결함 — **PC-006의 재발** (2026-08-29, 사용자 지적)

> "텍스트 구간 목록은 뷰어 크기와 같은 높이로 하고 스크롤 추가해줘"

원인이 **둘**이었고, 하나가 다른 하나를 가리고 있었다.

### ① 스크롤 규칙이 한 번도 적용된 적이 없다 — 클래스 이름 불일치

```css
[role="listbox"].section-list { overflow-y: auto; flex: 1; }   /* app.css */
```
```js
class: 'wh-feat-section-list'                                   /* app.js — section-list가 없다 */
```

`app.js`는 앵커 클래스만 붙였다. **선택자가 한 번도 매치되지 않았고**, 132행이 그대로
펼쳐져 목록이 **4536px**가 됐다.

이것은 PC-006에 기록된 "실 트랙 132행에서 SVG가 4566px가 된 결함"과 **같은 결함**이다.
그때 CSS 쪽은 고쳤는데 클래스가 붙지 않아 실제로는 고쳐지지 않았다. 기록만 보면
닫힌 것으로 보인다.

### ② `#app` 높이가 배너 높이를 상수로 가정했다

```css
#app { height: calc(100vh - 40px); }
```

충실도 배너는 `#app` **바깥**에 있고, 폭이 좁으면 두 줄로 접혀 40px을 넘는다. 그만큼
문서가 세로로 넘쳐 **페이지 전체가 스크롤**됐다(문서 4732px / 창 578px).

`body`를 flex 칼럼으로 두고 `#app`이 **남는 높이 전부**를 받게 바꿨다. `overflow-y`만
잠가 가로 스크롤(min-width 960px 규칙)은 유지된다.

### 실측

| 항목 | 전 | 후 |
|---|---|---|
| 문서 높이 / 창 높이 | 4732 / 578 (페이지 스크롤) | **578 / 578 (스크롤 없음)** |
| 목록 패널 높이 | — | **223px = 캔버스 223px** |
| 목록 내부 스크롤 | 없음 (4536px 펼침) | **있음** (clientH 177 / scrollH 4536) |

### 하네스 관찰 (PC-009·PC-010에 이어)

**같은 계열이 세 번째다.** 공통 성질은 여전하다 — *없어진 동작은 화면에 흔적을 남기지
않는다.* 이번엔 한 걸음 더 나쁘다: **결함이 "고쳐진 것으로 기록돼 있었다."** CSS 규칙은
정확했고 결정 로그도 남아 있었는데, 그 규칙을 받을 클래스가 마크업에 없었다.

필요한 단언은 스크린샷이 아니라 **선택자가 실제로 매치되는지**다. 이번에 쓴
`document.querySelector('.section-list')`가 null이었다는 사실이 그 단언의 초안이다.
`data-wh-anchor`가 붙은 요소는 스타일 클래스도 함께 검사해야 한다.


## PC-013 (2026-08-31) — 스트립·자동재생 조작 시 구간 목록 자동 스크롤·roving 포커스 동기화
- 트리거: 기능 변경 (/feature-add "상대 스케일 포커스 시에 동일한 구간 목록으로 스크롤되고 포커스")
- 대상: FEAT-013, 화면 3D 표시(TrackScreen)·WebGL 미지원 대체 화면
- 변경: 스트립 스크럽/키보드·자동재생(canvas)으로 공유 커서가 바뀌면 목록이 해당 행으로 스크롤(block: nearest)되고 그 행이 roving 포커스가 된다. DOM 포커스는 목록이 이미 포커스를 가질 때만 이동(기존 규칙). source `list`는 스크롤을 건드리지 않는다. 종전에는 강조(aria-selected)만 되고 132행 목록이 스크롤되지 않아 강조 행이 화면 밖에 남았다.
- 근거·승인: 사용자 승인 (Phase 1 체크포인트, 2026-08-31 — "스트립+자동재생 모두")
