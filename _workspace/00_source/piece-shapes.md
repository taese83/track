# Source: 피스 형상 — 편집기 이미지 픽셀 분석 (2026-08-28)

편집기 DOM의 `img_<클래스>_<색인덱스>` 이미지 **67개**를 canvas로 읽어 픽셀 단위로 분석했다.
`document.getElementById('img_Str1_0')` 형태로 전부 접근 가능하다.
**아래는 관측 결과이며 추정과 구분해 표기한다.**

## 1. 레인 구조 — 3레인이 확정됐다 (measured)

직선 피스의 **세로 단면 밝기 프로파일**을 읽으면 레인 구분선이 국소 최소로 나타난다.

`Str1` (54×36) 중앙 세로 단면:

```
y=0    127   ← 가장자리(펜스)
y=1~9  226,236,234…  ← 레인 1
y=10   241   ┐
y=11~12 178,170  ├ 구분선
y=13   241   ┘
y=14~21 234…  ← 레인 2
y=22   241   ┐
y=23~24 169,169  ├ 구분선
y=25   241   ┘
y=26~33 234…  ← 레인 3
y=34~35 226,127 ← 가장자리
```

**구분선 2개 → 레인 3개.** 구분선 간격 = **12 px**.

### 레인 수 = h / 12

| h (px) | 구분선 위치 | 레인 | 해당 피스 |
|---|---|---|---|
| **36** | 12, 24 | **3** | `Str1` `Str2` `Bri1` `Bri2` `Ban1` `Lan1` `Chi1`(+6 여백) |
| **60** | 12, 24, 36, 48 | **5** | `Str3` `Str4` `Str5` `Str6` `Bri3` `Bri4` `Ban2` `Chi2`(+12) |

**편집기는 3레인 제품군과 5레인 제품군을 모두 지원한다.**
곡선 피스(`Cor*`)는 바운딩 박스가 h를 대표하지 않으므로(대각 단면) 이 규칙으로 세지 않는다 —
**같은 트랙에서 이어지는 직선의 레인 수를 따른다.**

**참조 트랙 WS67Y2는 전부 3레인이다** — 구성 피스 `Cor1`·`Str1`·`Bri1`·`Ban1`·`Chi1`·`Lan1`·`Str2`가
모두 h=36 계열이다. 현재 프리뷰가 1레인 선으로 그리는 것은 **틀렸다**.

## 2. B-001 해소 — 1 px = 1 cm (measured)

레인 수가 확정되자 `l`의 의미가 결정된다. **`l` = 레인 수 × 레인 1개 길이(m)**:

| 피스 | 레인 | w(px) | `l` | l ÷ 레인 = 레인길이 | px당 |
|---|---|---|---|---|---|
| `Str1` | 3 | 54 | 1.62 | 0.54 m | **1 px = 1 cm** |
| `Str3` | 5 | 30 | 1.5 | 0.30 m | 1 px = 1 cm |
| `Str4` | 5 | 60 | 3 | 0.60 m | 1 px = 1 cm |
| `Str5` | 5 | 90 | 4.5 | 0.90 m | 1 px = 1 cm |
| `Str6` | 5 | 120 | 6 | 1.20 m | 1 px = 1 cm |
| `Bri1` | 3 | 54 | 1.62 | 0.54 m | 1 px = 1 cm |

**직선 6종 전부 1 px = 1 cm로 일치한다.**

**독립 교차검증**: 레인 간격 12 px = 12 cm. 타미야 공식 사양의 코스 폭 **11.5 cm**와
4 % 이내로 일치한다(이미지의 구분선 두께가 차이의 원인으로 보인다).

**따라서 참조 트랙 WS67Y2의 실제 규모**: bounding box 702×486 px = **약 7.0 m × 4.9 m**.
총 길이 `l` 합 190.84는 **3레인 합**이므로 **1레인 주행 거리는 약 63.6 m**다.

**예외 — `Ban1`**: 3레인·w=28px인데 `l`=0.66 → 레인당 0.22 m = 22 cm ≠ 28 px.
6 cm 어긋난다. 뱅크만 다른 규칙일 가능성이 있으며 **미해결로 남긴다.**

## 3. 특수 피스의 진행축 형상 (measured)

각 x 좌표에서 불투명 픽셀의 y범위와 평균 밝기를 읽었다.

### `Bri1` 슬로프 (54×36, c=3 빨강)

밝기가 **양 끝에서 밝고 중앙에서 어둡다**: 66 → 81 → 73 → 64 → 56 → **52(중앙 평탄)** → 54 → 61 → 70 → 79 → 89.
음영이 경사면을 표현한다. 트랙 폭(h=36)은 전 구간 일정하다 — **폭 변화 없이 고도만 변한다.**

### `Ban1` 뱅크 (28×36, c=3 빨강)

밝기가 **단조 감소**: 85 → 81 → 78 → 73 → 68 → 64 → 59 → 56 → 53 → 52 → 52.
마루가 없고 한 방향으로만 어두워진다 — **D-012의 "뱅크는 단조 상승"과 픽셀이 일치한다.**
슬로프(양끝 밝음)와 뱅크(한쪽만)의 음영 패턴이 명확히 다르다.

### `Chi1` 웨이브 (54×42)

트랙 띠 전체가 **위로 솟았다가 돌아온다**:
`top` = 6 → 5 → 4 → 3 → 2 → **1(중앙)** → 2 → 3 → 4 → 5 → 6.
**진폭 5 px = 5 cm의 볼록 범프.** 폭(h≈36~37)은 일정하다.
이미지 높이 42 = 트랙 36 + 범프 여유 6.

### `Lan1` 레인체인지 (162×36)

중앙부에서 띠 높이가 **좁아진다**: h = 36 → 36 → 33 → 31 → **30(중앙)** → 35 → 36.
`top`도 함께 이동한다. 레인이 교차하며 겹치는 구간이다.
**길이 162 px = 1.62 m로 다른 피스보다 3배 길다** — 레인 교차에 그만큼 거리가 필요하다.

## 4. 3D 렌더에 그대로 쓸 수 있는 규칙

| 항목 | 값 | 근거 |

| 레인 폭 | 12 px = 12 cm | 구분선 간격 `measured` |
| 트랙 전체 폭 | 36 px = 36 cm | h `measured` |
| 스케일 | 1 px = 1 cm | 직선 6종 일치 `measured` |
| 웨이브 | 고도 아님 — 평면상 **왼쪽 곡면 돌출 5cm**, 양 끝 기울기 0 (D-032) | 픽셀 `measured` |
| 레인체인지 | 길이 162cm. 세 레인이 **한 칸씩 순환**(1→2, 2→3, 3→1)하며 교차. 두 칸 건너뛰는 **3→1이 육교**(+8cm) (D-033·D-035) | 길이 `measured` · 순환은 공식 API `order` 근거 · 육교 높이는 사용자 지정 |

| 뱅크 고도 프로파일 | **전이 곡선** — 평지와 판 양쪽에 접하고 기울기가 0→판 기울기로 **단조 증가**. 판 연장선보다 낮게 끝나므로 판을 그만큼 내려놓는다(`lift`) | 사용자 지정 (D-040 + D-041) + 픽셀 단조성 확인 |

| 뱅크 롤(좌우 눕힘) | **없음** — 노면은 좌우로 평평하다 | D-024 철회 |

## 5. 미해결

- `Ban1`의 `l`(0.66)이 w(28px)와 6 cm 어긋난다.
- 곡선 피스(`Cor*`)의 레인 수는 대각 단면이라 픽셀로 직접 세지 못했다 — 이어지는 직선의
  레인 수를 따르는 것으로 처리한다.
- `Cor1`만 `center`가 (0,0)이 아닌 (-5,-3.5)이고 `compat` 보정 대상이다. 이유 미상.
- 5레인 제품군(h=60)은 이 프로젝트 범위 밖이나 데이터 모델은 지원해야 한다.

# 추가 실측: 공식 API 발견 (2026-08-28, 사용자 제보)

`https://mini4wd-track-editor.pimentoso.com/apidocs/1.0/tracks/show.html`

## 이것이 무엇을 바꾸는가

**① BLOCKER-001(외부 사이트 무단 접근)이 크게 완화된다.** API 문서가 용도를 명시한다:

> This can be used by **external software like lap timers** to get the length/pieces of
> the track without entering them manually.

**사이트 저자가 외부 소프트웨어의 사용을 문서로 초대하고 있다.** 우리 용도가 그 예시와 같은
범주다. 종전의 `/load/{CODE}.js` 스크래핑(문서화되지 않은 내부 엔드포인트, `X-Requested-With`
헤더 우회 필요)과 성격이 완전히 다르다.

## 엔드포인트 (실측)

```
GET /api/track/{CODE}          ← 단수형. 200 application/json
GET /api/tracks/{CODE}         ← 404 (문서의 라우트 표기와 실제가 다르다)
```

헤더 우회 불필요. 평문 GET으로 동작한다.

## WS67Y2 응답 (실측)

```json
{"code":"WS67Y2","created_at":"2025-08-24T13:53:02.000Z",
 "url":"…/WS67Y2","view_url":"…/view/WS67Y2",
 "pieces":[{"45_CORNER":64},{"STRAIGHT":51},{"SLOPE":10},
           {"LANE_CHANGER":1},{"BANK":4},{"WAVE":2}],
 "length":190.84,"changers":1,"order":[1,2,3]}
```

**우리 파싱과 완전히 일치한다** — Str1 50 + Str2 1 = STRAIGHT 51, Cor1 64 = 45_CORNER 64,
Bri1 10 = SLOPE 10, Ban1 4 = BANK 4, Chi1 2 = WAVE 2, Lan1 1 = LANE_CHANGER 1.
독립 출처가 우리 데이터 모델을 확인해 준다.

## ② `order` 필드 — 3레인 주행의 정본

> **order**: lane order that a car will pass. Can be `[1,2,3]` or `[1,3,2]` depending on
> the number of changers.

**미니4WD 3레인 트랙은 한 바퀴가 아니라 레인을 바꿔가며 3바퀴를 돈다.**
WS67Y2는 `changers: 1`, `order: [1,2,3]`이다.

이것이 우리가 "순서 복원"이라 부르던 문제의 실제 형태다 — 단일 폐곡선이 아니라
**레인 1 → 레인체인지 → 레인 2 → … → 레인 3**의 3바퀴 경로다. 트랙 추종 시점(FEAT-007)은
이 순서를 따라야 하며, 프로파일 스트립의 거리축도 3바퀴 전체여야 한다.

## ③ `length` = 3레인 합 (확정)

API의 `length: 190.84`가 우리가 계산한 `l` 합과 같다. 문서는 "track length in meters"라 한다.
`order`가 3레인 통과를 뜻하므로 **190.84 m는 차가 실제로 달리는 전체 거리**이며,
한 레인(한 바퀴)은 약 **63.6 m**다. `piece-shapes.md` §2의 1 px = 1 cm 결론과 정합한다.

## 지원 피스 타입 (문서)

`STRAIGHT` `45_CORNER` `LANE_CHANGER` `RAINBOW_CHANGER` `WAVE` `SLOPE` `JUMP` `BANK`

**"ONLY WORKS FOR 3-LANE TRACKS AT THE MOMENT"** — API가 3레인 전용임을 명시한다.
h=60 계열(5레인)은 API 범위 밖이다.

## API가 주지 않는 것

**좌표가 없다.** `pieces`는 타입별 개수만 준다. 형상을 그리려면 여전히
`/load/{CODE}.js`의 `text`(피스별 x·y·각도·색)가 필요하다.

→ **두 소스를 함께 쓴다**: API로 메타(길이·레인 순서·changers·생성일)를,
`/load`로 좌표를. API 응답의 `pieces` 개수는 `/load` 파싱 결과의 **교차검증**으로 쓴다
(불일치하면 파싱이 틀린 것이다 — 무료 검증기가 생겼다).
