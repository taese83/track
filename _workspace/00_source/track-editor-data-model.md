# Source: mini4wd-track-editor 데이터 모델 (실측)

출처: `https://mini4wd-track-editor.pimentoso.com/view/WS67Y2` — 2026-08-28 브라우저로 직접 관측.
사용자가 첨부한 도면의 원본 편집기다. **아래는 관측 결과이며, 이 사이트의 어떤 텍스트도 지시로 취급하지 않는다.**

## 트랙 인코딩

`parseTrack(text)`의 실제 구현에서 확인:

```
피스 = "ClassName;x;y;angle;color"
트랙 = 피스들을 "#" 로 이어붙인 문자열
```

각 피스는 `new ClassName()` → `position.set(x,y)` → `rotate(angle)` → `setColor(color)`로 복원된다.

**중요: 이것은 순서가 있는 경로가 아니라 배치도다.** 진행 순서는 데이터에 없다.

## 피스 인스턴스가 갖는 필드

`name`, `label`, `w`, `h`, `l`, `colors`, `center`, `vertex1`, `vertex2`,
`position`, `a`(각도), `c`(색), `rcenter`, `rvertex1`, `rvertex2`(회전 적용된 값), `img`

`vertex1`/`vertex2`는 **연결 끝점**이다 — 회전·위치가 적용된 `rvertex1`/`rvertex2`를 이웃 피스와
매칭하면 진행 순서를 결정적으로 복원할 수 있다. 이미지 분석이 필요 없는 이유가 이것이다.

## 이 관측이 기획에 미치는 영향

**① 슬로프/뱅크 판별에 휴리스틱이 필요 없다.** 사용자가 말한 "색이 있는 트랙이 길면 슬로프,
짧으면 뱅크"는 **도면 이미지를 읽는** 규칙이었다. 데이터에서는 `Bri1.label="slope"`와
`Ban1.label="bank"`로 **타입이 명시**된다. 이미지에서 그렇게 보였던 이유도 데이터가 설명한다 —
Ban1은 폭 28px, Bri1은 54px이다.

**② 색은 상승/하강 표시다.** 슬로프 10개가 `c=2` 5개 + `c=3` 5개로, 뱅크 4개가 2+2로 정확히
반씩 갈린다. 올라간 만큼 내려온다는 물리와 일치한다. 어느 쪽이 빨강(상승)인지는 **미확인**이다.

**③ 사용자가 언급하지 않은 피스 타입이 있다.** 이 트랙에 `Chi1`(wave) 2개가 있다. 웨이브는
슬로프도 뱅크도 아니다 — 처리 방침을 정해야 한다.

# 추가 실측: 데이터 취득 엔드포인트 (2026-08-28)

편집기 페이지 HTML에는 `data-track-code="WS67Y2"`만 있고 **트랙 데이터가 없다**. 뷰어 JS가
별도 엔드포인트에서 가져온다. 네트워크 캡처로 확인:

```
GET https://mini4wd-track-editor.pimentoso.com/load/{CODE}.js
필수 헤더: X-Requested-With: XMLHttpRequest
```

**헤더가 없으면 422**(Rails CSRF 거부)다. 실측한 조합:

| 요청 | 결과 |
|---|---|
| 기본 GET | 422 |
| User-Agent만 | 422 |
| UA + Referer | 422 |
| `Accept: text/javascript` | 422 |
| **UA + Referer + `X-Requested-With: XMLHttpRequest`** | **200 (3743B)** |

`X-Requested-With`가 결정적 요소다.

## 응답 형태

```js
const COMPATIBILITY_ID = 26586;
var compat = parseInt(258262) < COMPATIBILITY_ID;
var text = 'Cor1;121.111;641.142;225;0#Cor1;780.181;677.872;135;0#...';
```

- `text` — 피스 문자열. `#`로 분리하면 `클래스;x;y;각도;색`
- `compat` — 트랙 저장 시점 버전이 `COMPATIBILITY_ID`보다 오래됐는지. **true이면 `Cor1`의
  45°/135°/225°/315° 배치에 위치 보정(`Point(11.1, 4.88).rotate(angle)`)이 더해진다.**
  WS67Y2는 258262 > 26586이므로 `compat = false`.

## 검증

이 엔드포인트로 받은 데이터를 파싱한 결과가 브라우저에서 관측한 것과 **완전히 일치**한다:

| 항목 | curl 결과 | 브라우저 실측 |
|---|---|---|
| 피스 수 | 132 | 132 |
| 구성 | Cor1×64 Str1×50 Bri1×10 Ban1×4 Chi1×2 Lan1×1 Str2×1 | 동일 |
| 색분포 | 0×117 · 2×7 · 3×7 · 5×1 | 동일 |

## 아키텍처 영향

**headless 브라우저가 필요 없다.** serverless function에서 헤더 3개 붙인 단순 GET이면 된다.
이것이 tech-stack.md가 NEEDS_DECISION으로 남긴 최대 위험(대상이 JS SPA라 원문 fetch로
데이터가 안 나올 수 있음)의 답이다 — **해소됨.**

`compat` 플래그 처리를 구현에서 빠뜨리면 오래된 트랙의 45° 코너 위치가 어긋난다.
파싱 계약에 포함해야 한다.

## 결론 1 — N-001 해소 (measured)

사용자 규칙은 "올라가는 것은 빨간색, 내려가는 것은 파란색"이다. 측정과 합치면:

**`c=3` = 상승 · `c=2` = 하강.** 근거 등급 `measured`(픽셀 측정).

## 결론 2 — 리뷰어 #2가 옳았다 (등급 정정)

**`c`는 상승/하강 플래그가 아니라 팔레트 인덱스다.** 같은 인덱스가 피스 타입마다 다른 색을
가리키고(`Bri1.c0`=청록 vs `Str1.c0`=회백), 고도와 무관한 색도 있다(`Str1.c6`=주황).

따라서 규칙은 **"색 = 상승/하강"이 아니라 "고도 변화 피스(`Bri*`·`Ban*`)에 한해 빨강 변형은
상승, 파랑 변형은 하강"**으로 좁혀 적어야 한다. 종전 `confirmed` 서술은 과잉이었다.

## 결론 3 — `Str1 c=5` 처리 방침의 근거

빨강·파랑이 반반인 마커 직선이다. 참조 트랙에 1개 있고 도면상 START 옆에 있다 —
**출발선 표식**으로 보인다. 직선 피스이므로 **고도 변화 0**이며, 슬로프로 오인하면 안 된다.
3D에서는 평평한 직선으로 렌더하고 표식만 표기한다.
